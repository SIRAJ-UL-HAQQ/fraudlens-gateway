# Machine Learning Conventions and Constraints (PaySim)

ROLE: ML engineer.
MODE: Planning. This is research code: reproducibility and honest reporting matter more than raw performance.

## Constraints
- Global seed config; every experiment is runnable via a CLI:
  `python -m ml.src.train --model xgboost --strategy class_weight --seed 42`.
- Split chronologically on `step` (e.g. first 70% of steps train, remainder test). Resample TRAIN only. No test-set information in preprocessing statistics.
- Drop leakage-prone or non-generalising columns and document why: `isFlaggedFraud` (it is PaySim's own rule output), and raw account IDs. If you keep ID-derived features such as counts, compute them using past data only.
- Report the exact fraud ratio from the data in the EDA output. Never hardcode the fraud ratio; compute and report it from the data.

## PaySim Specifics to Handle and Document
- Fraud appears only in TRANSFER and CASH_OUT. Decide whether to train on those types only and justify the choice with the EDA numbers.
- Destination balance columns are zero for merchant accounts. Handle explicitly.
- Engineered features: balance deltas and balance-error features (`old_balance_orig - amount - new_balance_orig`, and the same for the destination), hour-of-day from step, type encoding.
- Warn me clearly: the balance-error features can make the task nearly separable. Report results with and without them so the comparison stays meaningful.
